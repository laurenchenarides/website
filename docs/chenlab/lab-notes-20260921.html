Getting started with Numerator: households, baskets, and sample coverage

Author

Lauren Chenarides

Published

September 21, 2026

Today’s goals

We will spend the first 30 minutes sharing project updates, questions, and current obstacles. We will use the remaining hour to cover:

  • how to read the Numerator entity-relationship diagram;
  • how the Numerator database, schemas, and Parquet source files are organized;
  • why we use DuckDB and how R connects to it;
  • how the household, basket, banner, and static reference tables relate;
  • how to interpret static-household membership, participation spells, and gaps;
  • how the available projection factors are intended to be used; and
  • how to begin the sample-flow diagnostics in R.

By the end of the lab, you should be able to connect R to the Numerator DuckDB database on Orchard, inspect the available tables, retrieve a household- or basket-level result, and close the connection. We will begin at the household and basket level; product-level work comes later.

Files for this lab

The following files will be available in the designated lab folder on Orchard. Copy them into your own R project before you begin. They are not distributed through the public website or GitHub repository.

  • config.R: open and close a read-only connection.
  • read_numerator.R: inspect columns and retrieve a small extract.
  • 03_sample_flow.R: run the sample-flow diagnostics from R and return the results as R data frames.

1. Reading an ER diagram

An entity-relationship (ER) diagram is a visual map of a database. Each box represents a table, the entries inside the box are its columns, and the lines show how tables can be connected. ER diagrams are useful because they help you find the variables you need, identify the columns used to join tables, and see whether a relationship is one-to-one or one-to-many before you write code.

When reading an ER diagram:

  1. Find the table that contains the outcome or observation you want to study.
  2. Read its column names and identify its ID fields.
  3. Follow a connecting line to see which ID links it to another table.
  4. Read the symbols at the ends of the line. A 1 means one matching record; a * means that several records may match.
  5. Ask what one row represents in each table. For example, one row may represent a household, a shopping basket, or an item within a basket.

We will walk through the supplied Numerator ER diagram together and use the example below to connect it to the tables we will use in R.

Example: Explain how these tables are related

Table Grain and purpose Key fields
people_table One current household record; home geography user_id, postal_code, census_region_name
summarylvl_fact_table One basket/trip; our main transaction table basket_id, user_id, banner_id, transaction_date, spending and order fields
banner_table One banner; add when interpreting retail channel banner_id, banner, channel, parent_channel

postal_code is the household’s current home postal code. store_postal_code is the store’s postal code. They answer different geographic questions. Preserve both as text so leading zeros survive. For historical residence, the dictionary describes people_history_table.FROM_DATE and UNTIL_DATE as demographic validity dates, not enrollment dates. We will need a validated time-varying join for that work.

The basket table includes basket_total (receipt total), basket_sub_total (pre-tax subtotal), basket_adjusted_subtotal, transaction dates, store geography, and order_method_type, order_provider, delivery_method_type, delivery_provider, and order_delivery_type. Choose an expenditure measure and document it. Retail channel comes from banner_table; ordering and fulfillment describe a different dimension. A grocery-store basket is not necessarily all food.

Before joining, check that the household and banner references have unique keys. The homework checks the candidate basket key (basket_id, user_id, banner_id, transaction_date). Joining baskets to all spells using only user_id repeats each basket for households with multiple spells. Use the one-row household view for household labels, or an explicit month match for monthly coverage. Item rows also repeat basket totals, which is why we start with the summary table.

Database structure

Numerator delivers the source data as Parquet files. Parquet is a compressed, column-based file format designed for large analytical datasets. The current release is stored in table-specific folders under D:\numerator\2026_07\. Keeping the vendor files in their original format gives us an unchanged source copy and lets DuckDB read only the columns and rows needed for a query.

The DuckDB database is stored at:

D:\numerator\Database\numerator

The database organizes its objects into schemas. A schema is a named section of a database, similar to a folder. It keeps tables with different purposes separate and allows two schemas to contain tables with the same name. In SQL and R, we identify a table with schema_name.table_name, such as core_new.people_table.

Our main schemas are:

Schema Purpose
core_new Current Numerator delivery. Its tables are views over the Parquet source files. Use this schema for the vendor tables in this lab.
core Earlier Numerator delivery retained for comparison. Do not use it unless a project specifically requires that release.
reference Shared classifications, crosswalks, and household reference tables that can be reused across projects.
diagnostics Reproducible checks and summaries built from the source data.
pb_project Tables created for the plant-based project. These are project-specific rather than general Numerator resources.

We keep shared reference tables in their own schema because some definitions require substantial setup and should be consistent across projects. For example, each student should not independently rebuild participation spells or retailer-channel classifications. A maintained table in reference can be created once, checked, and then read by many people. Transaction tables record purchases; reference tables describe, classify, or summarize the records used in those analyses.

Why DuckDB?

DuckDB is designed for analytical queries over large files. It can query Parquet directly, perform joins and summaries before data enter R, and return only the smaller result that you need. This matters because the full transaction tables are too large to load into R at once. DuckDB is also embedded: R opens the database file directly through the DBI package, so you can work from RStudio without running a separate database server. We use read-only connections so several people can query the shared database without changing its source tables.

2. Connecting R to DuckDB

Run R/RStudio inside your Orchard session. R connects directly to D:\numerator\Database\numerator. The database file has no extension, and its views depend on Parquet files stored elsewhere on Orchard, so copying only the database file to another computer is not enough.

Install the packages once into your own R library:

install.packages(c("DBI", "duckdb"))

At the start of each session, source the two helper files and open a connection:

source("config.R")
source("read_numerator.R")

con <- open_numerator_connection()
list_numerator_tables(con)
describe_numerator(con, "people_table")
describe_numerator(con, "summarylvl_fact_table")

config.R uses D:/numerator/Database/numerator by default. Forward slashes are used in R paths even though Windows displays the path with backslashes. The connection is read-only and fails if the database file is unavailable. Use one lab connection at a time, and always close it when you finish. The close helper disconnects and releases the database file. See the DuckDB R client documentation for additional connection details.

Read selected columns and a small preview:

households <- read_numerator(
  con, "people_table",
  columns = c("user_id", "postal_code", "census_region_name"), limit = 10
)

spells <- read_numerator(
  con, "static_household_spells", schema = "reference", limit = 10
)

baskets <- read_numerator(
  con, "summarylvl_fact_table",
  columns = c("basket_id", "user_id", "banner_id", "transaction_date",
              "basket_total", "store_postal_code", "order_method_type",
              "delivery_method_type", "basket_er_factor"),
  where = "transaction_date >= ? AND transaction_date < ?",
  params = list(as.Date("2025-01-01"), as.Date("2025-02-01")),
  limit = 100
)

close_numerator_connection(con)

The helpers cast identifiers to character inside DuckDB, before R can round a large DECIMAL(38,0) value, and return lowercase column names. A LIMIT preview is not a random or representative sample. The independently previewed tables need not contain matching households. For analysis, filter or aggregate in SQL first; even a one-month extract can be large. limit = NULL deliberately collects all rows matching your condition.

For a reusable script, put the work inside a function so the connection closes even if a query fails:

run_lab <- function() {
  con <- open_numerator_connection()
  on.exit(close_numerator_connection(con), add = TRUE)
  DBI::dbGetQuery(con, "
    SELECT date_trunc('month', transaction_date)::DATE AS month,
           COUNT(*) AS basket_rows, COUNT(DISTINCT user_id) AS households
    FROM core_new.summarylvl_fact_table
    WHERE transaction_date >= DATE '2025-01-01'
      AND transaction_date < DATE '2026-01-01'
    GROUP BY 1 ORDER BY 1
  ")
}
monthly_counts <- run_lab()

Only the small result enters R. The database does the scan and aggregation.

3. Static households and participation spells

“Static” generally refers to a sample selected for sustained reporting over a specified period. It does not mean that a household never moves, never changes, or participates forever.

Our internal draft describes Numerator’s official criteria in terms of consecutive reporting, qualifying receipts, demographic balance, and transcription completeness. It also says the relationship between those criteria and membership in static_table is unresolved. The older diagnostics implement a separate project proxy: at least 36 active months, at least 26 receipts, and a household-size spending floor, using gas-excluded activity in selected channels. Active months are not necessarily consecutive months. That proxy is not an official vendor classification.

ImportantThe operational definition for this exercise

For this lab, is_static_household = 1 means that the household appears in the supplied core_new.static_table. Call it static-file membership in your homework. This is not a verified official static-panel flag or proof of continuous reporting. The reference contains only members; use a left join from all observed households when comparing members and nonmembers.

The dictionary defines START_DATE and END_DATE as the endpoints of a 12-calendar-month static period. We index each record by the month of END_DATE, the trailing window’s endpoint, and identify consecutive runs of those monthly records. This labels weighting coverage; it does not establish that this is the correct month-matching rule for applying household weights to transactions.

The shared reference table reduces the source to one record per user_id and endpoint month, recording duplicate source-row counts for review. It starts a new spell whenever at least one endpoint month is missing. It does not fill all months inside every overlapping 12-month window, which would hide gaps between weighting records.

Consider a fictional household with endpoint months January, February, March, June, and July:

Spell First observed month Last observed month Months in spell Missing months before spell
1 January March 3 0
2 June July 2 2

This household has two observed coverage spells and returns after an April–May gap. Its overall January–July span contains five observed months, not seven continuously observed months. A single spell can still cover only a short portion of the full release.

The reference exposes observed_entry_month, observed_last_month, spell_start_month, spell_end_month, n_spells, gap_months_before, and is_return. The actual panel_entry_date and panel_exit_date remain NULL because the reviewed files do not establish them. touches_release_start and touches_release_end flag spells that reach the available static-file boundaries; activity may extend outside what we can observe.

A missing receipt is not proof that a household left the panel, and disappearance from the weighting file is not proof that it stopped purchasing. Returns may reflect renewed reporting or weighting eligibility. Attrition and changing sample composition can affect expenditure trends, event studies, and duration models. Compare unbalanced and continuously covered samples, but recognize that requiring future coverage can select survivors. Keep recent reporting lags in mind; low activity at the release boundary may reflect incomplete collection. Do not convert these gaps into verified enrollment events.

4. Projection factors and expenditure comparisons

The supplied dictionary describes the fields’ intended roles:

Field Where it lives Intended role
ER_FACTOR Item-level facts Extended-reach projection beyond the observed panel
BASKET_ER_FACTOR Basket-level facts Extended-reach projection of basket purchases
TREND_FACTOR / BASKET_TREND_FACTOR Corresponding fact table Trend-adjusted projection
DEMO_WEIGHT / NATIONAL_FACTOR static_table Demographic weighting / national scaling for the static reference population
WarningWhat we do not yet know

We do not yet have documentation explaining how Numerator constructs these weights: calibration targets, normalization, trimming, eligible populations, or how the factor families relate. Field descriptions explain intended use, but do not verify a national estimator for a chosen subset. We must confirm the applicable spending measure, population, period, and whether any factors combine before presenting national expenditure estimates.

The basic projection calculation to discuss is a sum of expenditures times their corresponding factor, if Numerator confirms that factor is the appropriate standalone multiplier:

\[ \widehat{E}_t = \sum_{b \in \mathcal{B}_t} E_b\,w_b, \qquad w_b = \text{BASKET\_ER\_FACTOR}_b. \]

For example, fictional baskets of $20 and $30 with factors 100 and 200 produce a raw total of $50 and an illustrative projected sum of $8,000. Dividing that sum by \(100 + 200\) gives a weighted mean basket expenditure, not national total expenditure or expenditure per household. At the item level, the analogous calculation would use item spending and ER_FACTOR; do not put an item factor on repeated basket totals.

Before calculating, inspect missing, nonfinite, zero, and negative factors, missing expenditures, and duplicate baskets. Do not replace missing factors with 1 or silently report a sum based on only the valid rows. Negative spending may represent returns and needs its own interpretation. This example reports factor coverage and returns an illustrative sum only when every basket has a finite positive factor and nonmissing spending:

summarize_projection_factors <- function() {
  con <- open_numerator_connection()
  on.exit(close_numerator_connection(con), add = TRUE)

  DBI::dbGetQuery(con, "
    SELECT
        date_trunc('month', transaction_date)::DATE AS month,
        COUNT(*) AS n_baskets,
        COUNT(*) FILTER (WHERE basket_total IS NULL) AS missing_spending,
        COUNT(*) FILTER (
            WHERE basket_er_factor IS NULL
               OR NOT isfinite(basket_er_factor)
               OR basket_er_factor <= 0
        ) AS invalid_factors,
        SUM(basket_total) AS observed_spending_nonmissing,
        CASE WHEN COUNT(*) FILTER (
            WHERE basket_total IS NULL
               OR basket_er_factor IS NULL
               OR NOT isfinite(basket_er_factor)
               OR basket_er_factor <= 0
        ) = 0
        THEN SUM(basket_total * basket_er_factor)
        END AS illustrative_er_weighted_sum
    FROM core_new.summarylvl_fact_table
    WHERE transaction_date >= DATE '2025-01-01'
      AND transaction_date < DATE '2026-01-01'
    GROUP BY 1
    ORDER BY 1
  ")
}

factor_summary <- summarize_projection_factors()

This R function opens the connection, sends the SQL query to DuckDB, returns the monthly summary to R, and closes the connection. Run the duplicate-key check in 03_sample_flow.R before treating baskets as unique. This illustration uses the full basket population in the date window, not the static/ZIP-filtered homework subset. Restricting to static-file members, known ZIPs, or continuously observed households changes the represented sample; supplied factors may not project that restricted sample nationally. Do not multiply ER, trend, demographic, and national factors together without explicit instructions from Numerator.

For national comparisons, align time periods, population, channels, tax treatment, and expenditure scope with the benchmark. Basket totals from grocery retailers cannot stand in for food spending without resolving nonfood purchases. Report raw counts and unweighted spending beside any projected calculation, examine changes in sample composition and missing weights, and distinguish nominal changes from inflation-adjusted changes. Weighting alone does not establish representative ZIP coverage or correct all attrition bias.

5. Homework: build the first sample-flow diagnostics

Complete the exercise in RStudio on Orchard. 03_sample_flow.R shows how R can send SQL to DuckDB with two DBI functions:

  • DBI::dbExecute() creates temporary working tables when no result needs to be returned.
  • DBI::dbGetQuery() runs a query and returns its result as an R data frame.

The large transaction data remain in DuckDB. Only the diagnostic summaries enter R. Start the exercise with:

source("03_sample_flow.R")

diagnostics <- run_sample_flow(
  date_from = as.Date("2025-01-01"),
  date_to = as.Date("2026-01-01")
)

names(diagnostics)
View(diagnostics$sample_flow)
View(diagnostics$geography_by_region)
View(diagnostics$monthly_coverage)

Use calendar year 2025 initially, after checking diagnostics$source_coverage and diagnostics$static_coverage. The end date is exclusive, so 2026-01-01 is not included. Keep the same period at every step and record the release used.

All observed households → static-file members → geographic coverage → coverage over time.

  1. All observed households: Use diagnostics$sample_flow to identify distinct nonmissing user_id values with a basket in the analysis window, across all channels, including gas-only baskets. This is an observed purchaser population, not every enrolled household or every row of people_table. Report missing IDs and dates from diagnostics$source_coverage separately.
  2. Static-file members: Report how many observed households appear in at least one static endpoint month within the same analysis window. Do not treat membership elsewhere in the full release as membership in 2025. Report the number retained, the number lost, and the share of the starting sample.
  3. Geographic coverage: Use diagnostics$geography_status and diagnostics$geography_by_region to report missing household records, missing postal codes, other postal formats, household counts, and distinct ZIP counts. The five-digit/ZIP+4 check establishes only a ZIP-shaped string; it does not validate a ZIP against a geographic crosswalk or measure population coverage.
  4. Coverage over time: Use diagnostics$monthly_coverage to make a line plot in R showing observed households, households with same-month static-file coverage, and those also passing the ZIP-format screen. Retain zero-count months. Use diagnostics$spell_distribution and diagnostics$coverage_cross_tab to compare participation patterns. Report the additional loss from requiring static coverage in every analysis month as a sensitivity check.

Bring to the next lab: one sample-flow table, one geography summary, one monthly line plot, and a short paragraph stating your inclusion rules and explaining a gap/return example. Submit the R code needed to reproduce them. Identify the largest source of sample loss and one reason it could affect your research question. Discuss whether a changing monthly count reflects purchase activity, weighting coverage, reporting lag, or something the available fields cannot distinguish.

The exercise deliberately keeps the number of basket-active months separate from the number of static-coverage months. No observed basket is not automatically zero spending. Homework counts are unweighted; national projection is a separate question. Keep household extracts and detailed geographic outputs on Orchard or other approved lab storage.

Questions to resolve before final estimates

The live DuckDB schema is the authority for the tables and column types currently available on Orchard. The supplied data dictionary describes the variables, but several methodological questions remain open. Before using these data for final estimates, we still need to confirm:

  • whether an official Numerator static-panel flag is available;
  • how to interpret months when a household is absent from the weighting file;
  • whether any available dates represent actual panel enrollment and exit;
  • how household weights should be aligned with transaction dates; and
  • how Numerator constructs and intends researchers to combine the projection factors.

The participation-spell reference gives us an auditable description of observed coverage under the current definition. It can be revised when additional documentation becomes available.
